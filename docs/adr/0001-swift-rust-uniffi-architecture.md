# ADR-001: Swift app over a Rust core, bridged with UniFFI

- Status: Accepted
- Date: 2026-10-07

## Context

Veya needs native playback powered by librespot, which is a Rust project
(MIT) with no officially supported C or Swift bindings. The app must be a
native SwiftUI/AppKit macOS client with no embedded web runtime, idle RAM
under 120 MB, and cold launch under 1 s on Apple silicon.

Options considered:

1. **Swift app + Rust core (`spotcore`) via UniFFI bindings.** Swift never
   touches librespot or Spotify protocol types directly; everything crosses
   the FFI boundary as plain records/enums generated by UniFFI.
2. **Hand-written C shim over librespot**, with Swift calling into it via a
   bridging header. More control, but all marshalling, memory management and
   async bridging would be written and maintained by hand.
3. **Reimplement the relevant Spotify protocol/session logic directly in
   Swift**, dropping librespot entirely. Avoids Rust/FFI complexity but means
   reverse-engineering and maintaining the private Spotify protocol
   ourselves - a much larger and riskier undertaking than wrapping an
   existing, actively maintained implementation.
4. **Ship a bundled helper process** (e.g. a Rust binary driven over
   stdio/IPC) instead of linking a static library. Simplifies the language
   boundary to message passing but adds process-management overhead,
   complicates sandboxing, and increases latency for frequent calls (seek,
   volume, position events).

## Decision

Go with option 1: a thin Rust crate (`spotcore`) wraps librespot and exposes
a small, stable API; UniFFI generates the Swift bindings (with async
support) consumed via a Swift package (`SpotCoreKit`) wrapping a built
xcframework. The Swift app calls `spotcore` only through these generated
bindings and never imports librespot types directly.

## Consequences

- librespot upgrades (e.g. the 0.8 `SpotifyId` → `SpotifyUri` change) are
  isolated to the Rust crate; Swift call sites are unaffected unless the
  `spotcore` API itself changes.
- Async Rust functions surface as Swift `async throws`; Rust errors map to a
  typed `SpotCoreError` enum, keeping error handling idiomatic on both sides.
- Adds Rust toolchain, UniFFI codegen, and an xcframework build phase to the
  build pipeline (tracked in PBI-002/PBI-003), increasing build complexity
  versus a pure-Swift app.
- Audio must still cross the FFI boundary efficiently; this ADR does not
  cover the audio path itself (see the native CoreAudio sink work, PBI-201).
